# CLAUDE.md

Project-specific guide for AI coding agents. Read [README.md](README.md) first for what the project is; this file covers invariants and landmines.

## One-line summary

Postern is a FastAPI portal + Nginx reverse proxy + per-connection Shadowsocks-rust containers. The portal reconciles Docker container state against its SQLite database.

## Architecture invariants

These are load-bearing. Changing any of them without understanding the chain will silently break the system. Line numbers below are accurate at the time of writing — if an edit has drifted them, re-locate by the quoted symbol.

- **Path-token chain.** All three must agree:
  - [nginx/etc/nginx.conf:36](nginx/etc/nginx.conf) regex `^/t/([a-f0-9]{24})$`
  - [portal/src/postern/cli.py:137](portal/src/postern/cli.py#L137) `secrets.token_hex(12)` (12 bytes → 24 hex chars)
  - [portal/src/postern/reconciler.py:29-30](portal/src/postern/reconciler.py#L29-L30) `f"ss-{conn.path_token}"`
- **Container name = DNS hostname.** Nginx proxies `http://ss-$1`, resolved via Docker's embedded DNS (`resolver 127.0.0.11` in nginx.conf). The `ss-` prefix is not cosmetic.
- **Reconciler is the source of truth.** DB state → container state. Connection creation is CLI-only (there is no `POST /connection` route). Reconciler responsibilities, all in [portal/src/postern/reconciler.py](portal/src/postern/reconciler.py):
  - Create missing containers, remove orphans
  - Restart exited containers (lines 111–120)
  - Recreate containers when the `local/shadowsocks-server` image ID changes (lines 122–139)
  - Clean up expired sessions/OTPs each pass (line 160 → `db.cleanup_expired`)
- **Reconciler is scoped to its own deployment.** Every container the reconciler creates carries `postern.managed=true` AND `postern.instance=<id>`; every listing it does (`reconciler._list_managed_containers`) filters on both, not `postern.managed=true` alone. Multiple Postern deployments (production, an e2e run, a second checkout) can share one Docker daemon, and a bare `postern.managed=true` filter would sweep and recreate every *other* deployment's `ss-*` containers as orphans. `<id>` comes from `reconciler.resolve_instance_id(settings)`: an explicit `INSTANCE_ID` override, else `Settings.compose_project_name` (auto-populated by `compose.yaml`'s `COMPOSE_PROJECT_NAME: ${COMPOSE_PROJECT_NAME:-}`, which Docker Compose itself resolves from `-p`/directory basename — zero operator config in the common case). Identity is resolved from configuration only, never by having the portal inspect its own running container via the Docker API — that would add a startup-time Docker dependency to the identity check itself. If neither is set, `resolve_instance_id` returns `None` and the reconciler fails safe: it skips ALL container creation/removal/restart that pass (session/OTP cleanup still runs), logs an error, and every state-mutating `postern` CLI command prints a `WARNING`. A create-time name conflict (409 against a container not in this instance's managed set) is never auto-removed — logged with `docker rm -f` guidance instead — unless the squatter already carries this exact instance's own label (a prior removal that silently failed, safe to retry). Containers from a portal that predates this labeling carry `postern.managed=true` with no `postern.instance` label; they are never auto-adopted by any instance and require a manual one-time migration after upgrading (see [docs/operations/index.md](docs/operations/index.md)).
- **Manual reconcile trigger.** The data directory (`dirname(database_path)`) is derived in exactly one place, [reconcile_wait.py](portal/src/postern/reconcile_wait.py) `data_dir` — `cli.py`'s `_trigger_reconcile`, the loop's `.reconcile-now` watcher, and the `.reconcile-waiters/` handshake below all route through it. Do not re-derive it anywhere. Two protocols live in that directory:
  - `.reconcile-now` — existence is the signal; the loop consumes and unlinks it. Written by `_trigger_reconcile`, which every state-mutating CLI command calls; the e2e helpers and operators go through `postern reconcile` rather than touching the file directly.
  - `.reconcile-waiters/` — the `postern reconcile --wait` completion handshake, implemented in [reconcile_wait.py](portal/src/postern/reconcile_wait.py) (stdlib-only on purpose, so `cli.py` does not import the Docker SDK for a protocol every invocation of the command touches). Full protocol walkthrough (why `flock` over an age threshold / PID / `/proc` scan, the snapshot-at-start / notify-at-end ordering, the shutdown-notify safety net) is in [docs/development/architecture.md](docs/development/architecture.md)'s "The reconciler" section — read it before touching this file. The invariant that belongs here: `snapshot_waiters`/`sweep_orphan_waiters`/`notify_waiters` must never raise (the loop's task is never inspected until shutdown, so an escape would leave a portal that answers `/healthz` and has silently stopped reconciling), and "pass finished" is not "state converged" — `reconcile()` returns normally when the tunnel image is missing.
- **Production runtime is distroless (portal only).** [portal/Dockerfile](portal/Dockerfile)'s runtime stage is `dhi.io/python:3.13-alpine3.23` (no `-dev`). It ships only Python and its bundled libs — no `sh`, no busybox, no `touch`/`cat`/`ls`/`id`, no apk. Anything that previously assumed a shell — entrypoint scripts, `docker compose exec ... <unix tool>` patterns, healthchecks using `[CMD-SHELL ...]`, runtime-stage `RUN` instructions — must be rewritten in Python or moved to the build stage (which is `-dev` and still has Alpine + apk). Container debugging via `docker compose exec portal sh` will fail; use `python -c '...'` (see [tests/e2e/\_helpers.py:47](portal/tests/e2e/_helpers.py#L47) `query_db` for the pattern) or an ephemeral debug container. The **shadowsocks** runtime ([shadowsocks/Dockerfile](shadowsocks/Dockerfile) on `dhi.io/debian-base:trixie`) is NOT distroless — it ships bash + coreutils and uses a real entrypoint script, and `docker run --init --entrypoint sh local/shadowsocks-server` works for debugging.
- **PID 1 is `tini`.** Every container in this repo runs with `init: true` (compose) or `init=True` (`docker.containers.run` in the reconciler). Docker injects `tini` at PID 1, which forwards signals and reaps zombies; the user process runs as PID 2. This matters for the **per-connection shadowsocks containers** (where `ssserver` spawns `v2ray-plugin` as a child that would otherwise zombify) and for the **distroless portal** (where there is no shell to act as init). Probe from the host with `docker inspect <name> --format '{{.HostConfig.Init}}'`; from inside the portal `/proc/1/exe` is root-owned and unreadable from the `nonroot` user, so use `/proc/1/comm` (world-readable) instead.
- **Instance scoping covers container listing, not the network.** Co-located deployments' `ss-*` containers share one bridge network unless each sets a distinct `SHADOWSOCKS_NETWORK` — a separate axis from `postern.instance`, opt-in not automatic. `compose.yaml` interpolates the identical `${SHADOWSOCKS_NETWORK:-shadowsocks}` for both `networks.shadowsocks.name` and the portal's own `environment:` entry, and the reconciler's recreate check covers a network mismatch as well as an image-ID change — see [docs/development/architecture.md](docs/development/architecture.md)'s "The reconciler" section for the full mechanism and self-heal runbook, pinned by [portal/tests/test_compose_reconciler_scoping.py](portal/tests/test_compose_reconciler_scoping.py).
- **Shutdown wipes all of this instance's `ss-*` containers, ordered after any in-flight pass.** [portal/src/postern/app.py](portal/src/postern/app.py)'s shutdown sequence is `request_reconcile_shutdown()` (sets a `threading.Event` an in-flight pass polls between container operations) → cancel the reconciliation loop task → `await wait_for_inflight_reconcile()` (blocks on the reconcile pass's own executor future — NOT the same as awaiting the cancelled task, which only detaches from the still-running thread) → `cleanup_all_containers(settings)`. This ordering exists because `asyncio.to_thread`/`run_in_executor` cancellation cannot stop an already-started thread: without the wait, a straggler create from an in-flight pass can run after the sweep has listed, or use-after-close the `DockerClient` that `reconcile()`'s own `finally` has since closed. `cleanup_all_containers` is scoped by the same `postern.managed=true` + `postern.instance=<id>` filter as the orphan sweep (see **Reconciler is scoped to its own deployment** above) — it never touches another deployment's containers. Cleanup is best-effort — exceptions are swallowed. If the docker-proxy is unavailable at shutdown, containers survive; the reconciler adopts them on the next pass via the same label pair. Do not assume containers persist across portal restarts in tests or in code.
- **Docker API access is proxied.** The portal uses `docker.DockerClient.from_env()` ([reconciler.py:34](portal/src/postern/reconciler.py#L34)), which reads `DOCKER_HOST=tcp://docker-proxy:2375` (set in [compose.yaml](compose.yaml)). The `docker-proxy` grants `CONTAINERS`, `NETWORKS`, `IMAGES`, `POST` verbs only. Never hardcode `/var/run/docker.sock`. If you add a new Docker API call that needs a different verb, enable it on the proxy.
- **Portal container is read-only.** `read_only: true` + `tmpfs: [/tmp]` + `no-new-privileges:true`. Writes go to `/data` (named volume) or `/tmp` (tmpfs). Nothing else is writable at runtime.
- **DB lives in the `postern-data` named volume, NOT `./data/`.** `./data/` is gitignored and not created anywhere in the repo — it is not a working directory. Tests use `tmp_path` (see [portal/tests/conftest.py](portal/tests/conftest.py)). Never hardcode `/data/postern.db` in tests or scripts.
- **SQLite PRAGMAs are load-bearing.** [db.py:51-53](portal/src/postern/db.py#L51-L53) sets `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`. Always go through `db.get_connection()`; never `aiosqlite.connect()` directly.
- **datetime adapter is registered at module import.** [db.py](portal/src/postern/db.py) calls `sqlite3.register_adapter(datetime, ...)` so `Session.expires_at` (typed `str | datetime`) and any future model that lets a Python `datetime` reach the aiosqlite boundary serialize to the same `YYYY-MM-DD HH:MM:SS` shape used by `auth.py`'s strftime path. Aware values are normalized to UTC; naive values raise `ValueError` (Postern is UTC-everywhere, and silently storing local time as UTC is a foot-gun). Removing the registration revives the Python-3.12 deprecation warning and breaks outright in 3.14+.
- **Constant-time comparisons.** OTP verification ([db.py:234](portal/src/postern/db.py#L234)) uses `hmac.compare_digest`. Never simplify to `==`.
- **Email-enumeration defence.** [auth.py:44-52](portal/src/postern/auth.py#L44-L52) always creates an OTP row, using `__dummy__{email}` for unknown emails, so timing and rate-limit buckets don't reveal which emails are registered. Do not remove the dummy path "for simplicity."
- **SMTP TLS mode is port-derived.** [email.py:33-34](portal/src/postern/email.py#L33-L34): `use_tls = port == 465`, `start_tls = port == 587`. Any other port means plaintext. If you add a new port, also update these conditions.
- **Session cookies require HTTPS.** `login.py` sets `secure=True`. Login cannot complete over plain HTTP. Local dev needs TLS — see [docs/development/index.md](docs/development/index.md).
- **Cookie names are load-bearing.** `otp_email` and `session` are referenced across `routes/login.py` and `routes/dashboard.py`. Renaming either breaks auth.
- **`ss_config.py` invariants.** [ss_config.py:10-11](portal/src/postern/ss_config.py#L10-L11) hardcodes cipher `chacha20-ietf-poly1305` and `SERVER_PORT=80`. Both must match what the Shadowsocks image accepts and what Nginx upstreams to. The `plugin_opts` strings are also load-bearing: server mode uses `server;fast-open;path=/t/{token};host={domain}`, client mode uses `tls;fast-open;path=/t/{token};host={domain}`, plus an ECH suffix emitted per-connection from `conn.ech`: `never` → nothing; `auto` → `;ech=auto;ech-doh={ECH_DOH_URL}` when `ECH_DOH_URL` is set, else nothing (opportunistic, degrades to plaintext); `always` → `;ech=always;ech-doh={ECH_DOH_URL}`, or a hard error if `ECH_DOH_URL` is empty (fail-closed cannot be honored). `server_config` never emits `ech`. galoshes forwards `ech`/`ech-doh` verbatim to its embedded ex-ray, so both plugins do ECH identically. The `path=` must match the Nginx regex; `host=` sets the TLS SNI that the plugin (ex-ray) validates. The `"plugin"` field is per-connection (`conn.plugin`, either `v2ray-plugin` or `galoshes`); the `plugin_opts` string is identical for both because galoshes passes the same options through to its embedded yamux layer AND its embedded ex-ray (galoshes v0.3.0 vendors ex-ray in place of v2ray-plugin). The `v2ray-plugin` binary is itself ex-ray — see the next invariant.
- **Two plugin binaries ship in the shadowsocks image.** [shadowsocks/Dockerfile](shadowsocks/Dockerfile) downloads **ex-ray** (from `bindreams/hole`'s `releases/ex-ray/` track) and **galoshes** (`releases/galoshes/`), SHA256-verified, and installs them at `/usr/local/bin/v2ray-plugin` and `/usr/local/bin/galoshes`. ex-ray is a wire-compatible v2ray-core SIP003 shim installed under the historical `v2ray-plugin` name, so the SS_CONFIG `plugin` value stays `v2ray-plugin` and clients are unaffected (`EX_RAY_VERSION` ARG; renovate tracks the ex-ray track). `ssserver` finds them by `plugin` name in the SS_CONFIG JSON. ECH (`ech`/`ech-doh` opts) requires ex-ray >= v0.2.0 / galoshes >= v0.3.0. Removing either binary breaks connections that selected it. Adding a third plugin requires (1) a new download stage in the Dockerfile, (2) a new value in the `Connection.plugin` `Literal` in [models.py](portal/src/postern/models.py) and `PluginChoice` enum in [cli.py](portal/src/postern/cli.py), (3) a NEW migration 4 in [db.py](portal/src/postern/db.py) extending the `CHECK` allowed-value set -- do NOT mutate migrations 1-3.
- **Per-connection ECH.** `connections.ech` (migration 3, `NOT NULL DEFAULT 'auto'`, `CHECK` in `('never', 'auto', 'always')`) is client-config-only, set via `postern connection add --ech never|auto|always`; there is no server-wide ECH toggle anymore (see the `ss_config.py invariants` bullet for how each mode renders). `connection add --ech always` self-checks the front via `postern.ech.check_apex_ech` before creating the connection: refuses on `absent`, warns (but proceeds) on `inconclusive`.
- **Zone-ECH is the fourth CF REST bypass.** [provisioner/postern-dns/cloudflare_ech.go](provisioner/postern-dns/cloudflare_ech.go) GET/PATCHes the Cloudflare zone-level `ech` setting (`postern-dns ech-set <domain> on|off`, cloudflare-only), reusing `cfClient` + `CLOUDFLARE_API_TOKEN` alongside `cloudflare_proxied.go` and `cloudflare_tlsa.go`. Gated on `ech_zone_enabled = edge_profile==cloudflare AND dns_provider==cloudflare AND edge_cf_manage_zone_ech` (see [enablement.py](portal/src/postern_provisioner/enablement.py)) — independent of per-connection ECH. `EDGE_CF_MANAGE_ZONE_ECH` now defaults **false** (opt-in): it is zone-WIDE, needs a `Zone Settings:Edit` CF token, and can break clients on hostile networks. Converge-to-ON only — the reconciler never calls `ech-set off` (auto-reverting could break unrelated zone services). The provisioner healthcheck ([healthcheck.py](portal/src/postern_provisioner/healthcheck.py)) reports unhealthy until the PATCH has succeeded once (state in `ech_zone_state.json` on the **`postern-mta-data` volume** — NOT the nginx-inotify-watched edge volume, and the only volume both the provisioner and the portal mount), NOT on live DoH propagation. That unhealthy signal is a hard nginx/mta startup gate only under `compose.cert.yaml` (where they `depends_on` the provisioner); in the default BYO-cert mode it is signal-only (unhealthy container + logs + `postern ech verify`). Verifying that CF actually serves `ech=` is **portal-only**: a DoH check of the apex HTTPS `ech=` SvcParam ([postern/ech.py](portal/src/postern/ech.py)) backs `postern ech verify`/`show` (DoH-only, no CF token in the portal; needs the `dnspython[doh]` backend). The provisioner does NOT run this check — its image ships no DoH backend.
- **Zone SSL/TLS mode is the fifth CF REST bypass.** [provisioner/postern-dns/cloudflare_ssl.go](provisioner/postern-dns/cloudflare_ssl.go) GET/PATCHes the Cloudflare zone-level `ssl` setting (`postern-dns ssl-set <domain> full|strict`, cloudflare-only), reusing `getZoneSetting`/`patchZoneSetting` from `cloudflare_ech.go`. Gated on `ssl_mode_enabled = edge_profile==cloudflare AND dns_provider==cloudflare AND edge_cf_manage_ssl_mode` — structurally identical to `ech_zone_enabled`, but `EDGE_CF_MANAGE_SSL_MODE` defaults **true** (opt-out), UNLIKE zone-ECH's opt-in default, because a Flexible/Off zone is a hard `ERR_TOO_MANY_REDIRECTS` breakage (`MANAGE_SSL_MODE_DEFAULT` / `MANAGE_ZONE_ECH_DEFAULT` in enablement.py are shared so healthcheck.py + entrypoint.py can't diverge). **Raise-only** (floor `full`): raise `off`/`flexible` to the `EDGE_CF_SSL_MODE` target (`strict` default), leave `full`/`strict` untouched. Every PATCH is a raise vs the read value, so the default `strict` never lowers a mode; `target=full` carries an accepted GET→PATCH race (CF has no CAS) that can clobber a concurrently-set `strict`→`full` — the guarantee is "only ever raises", not race-free "never downgrades". Converge-only, zone-WIDE (never reverts/turns off). State in `ssl_mode_state.json` on the **`postern-mta-data` volume** (same as ECH). The provisioner healthcheck ([healthcheck.py](portal/src/postern_provisioner/healthcheck.py)) reports unhealthy until the set has succeeded once — a hard nginx/mta startup gate only under `compose.cert.yaml` (same as ECH). Because it is default-on, the provisioner token **must** have `Zone Settings:Edit`; a narrower `DNS:Edit`+`Zone:Read` token 403s and, under `compose.cert.yaml`, blocks nginx/mta startup (see the edge.md pre-upgrade warning). `postern edge ssl-status` (portal, DoH-free — SSL mode is not DNS-observable) reads the state file only; the portal has no CF token. `ssl-set` prints the mode CF left the zone in; the reconciler persists it as `last_observed_mode`, and `ssl-status` prints it as `zone_ssl_current_mode` so an operator sees target-vs-actual drift (e.g. target `strict` but a raise-only no-op left an already-`full` zone at `full`).
- **Shadowsocks runtime is `dhi.io/debian-base:trixie` (glibc 2.41), NOT `alpine-base`.** Galoshes' pre-built binary is dynamically linked against glibc 2.39+, so we cannot use Alpine/musl. The image still ships busybox-equivalent tools (`/bin/sh` is bash on debian) plus the entrypoint script. `docker run --rm -it --init --entrypoint sh local/shadowsocks-server` still works for debugging. The ssserver build stage uses `dhi.io/rust:1-debian13-dev` (no `musl-dev` apk needed).
- **OpenAPI is disabled on purpose.** [app.py:22](portal/src/postern/app.py#L22): `docs_url=None, redoc_url=None, openapi_url=None`. There is no public API surface. Do not re-enable.
- **Pydantic settings are env-case-insensitive.** `.env` uses `UPPER_SNAKE_CASE`; Python code reads `settings.lower_snake_case`. They refer to the same field.
- **Auth flow spans two places.** `OTP_EXPIRY_SECONDS` (default 600) controls the OTP's DB lifetime, but the `otp_email` cookie's `max_age` is hardcoded to 900 in [routes/login.py:42](portal/src/postern/routes/login.py#L42). Changing the setting without updating the cookie can leave a cookie pointing at an expired OTP (or vice versa). Keep them in sync.
- **Adding an auth route requires an nginx block.** The `auth` rate-limit zone is applied per-`location` in [nginx/etc/nginx.conf](nginx/etc/nginx.conf) — currently only on `/login` and `= /login/verify`. A new route like `/signup` or `/reset-password` will bypass rate limiting unless you add a matching `location` block with `limit_req zone=auth burst=5 nodelay;`.
- **E2e nginx auth rate limit diverges from production on purpose.** [portal/tests/e2e/nginx.conf](portal/tests/e2e/nginx.conf) uses `rate=600r/m, burst=20`; production [nginx/etc/nginx.conf](nginx/etc/nginx.conf) uses `rate=10r/m, burst=5`. The divergence exists because all e2e tests share a single source IP and the production rate exhausts the bucket mid-suite (GitHub issue #7). The boundary is pinned by `test_login_rate_limit_has_suite_burst_headroom` in [portal/tests/e2e/test_tunnel.py](portal/tests/e2e/test_tunnel.py); if you tighten the e2e rate, expect that test (and then the rest of the suite) to fail. If you add a new auth `location` to the e2e config, mirror the burst there too — it must stay `>= 20`.
- **The e2e server PKI must be ECDSA, not Ed25519.** [portal/tests/e2e/\_certs.py](portal/tests/e2e/_certs.py) `generate_test_pki` issues a P-256 CA + leaf. ex-ray >= v0.2.0 dials through uTLS imitating Chrome (`defaultFingerprint = "chrome_auto"`), and Chrome's `signature_algorithms` extension offers ECDSA and RSA but never ed25519 — against an Ed25519 chain nginx answers `no suitable signature algorithm` and every tunnel test dies at the TLS handshake, surfacing only as `curl: (52) Empty reply from server`. The CA matters as much as the leaf: the client verifies the CA's signature over the leaf. P-256 is also what Let's Encrypt issues, so the harness matches production. Pinned by `test_keys_are_ecdsa_p256` in [portal/tests/test_certs_unit.py](portal/tests/test_certs_unit.py). `generate_edge_client_pki` (mTLS client certs, validated by nginx rather than by uTLS) is still Ed25519 and is fine.
- **Shadowsocks build context is the repo root, not `./shadowsocks/`.** [shadowsocks/Dockerfile](shadowsocks/Dockerfile) `COPY`s from `external/shadowsocks-rust/` (which lives outside the Dockerfile's directory) and downloads `v2ray-plugin` + `galoshes` from `bindreams/hole` release assets at build time. Build with `docker build -f shadowsocks/Dockerfile --build-arg GIT_REVISION="$GIT_REVISION" -t local/shadowsocks-server .` from the repo root (see **Build provenance** below for `$GIT_REVISION`). A `docker build ./shadowsocks/` command will fail.
- **E2e images carry a `-test` suffix on the name; production is unsuffixed.** Docker image tags are host-wide, so an e2e run that reused a production tag would silently replace the image a production `docker compose up -d` deploys. The suffix goes on the image *name* (`local/nginx-test`), never the tag (`local/nginx:e2e`) and never a separate namespace (`local-e2e/nginx`) — `local/` is reserved for locally-built images with no online equivalent, and a tag means "version" everywhere in this repo. Everything the e2e suite builds or runs is `local/<name>-test`: the four e2e compose files' `image:` fields, the constants in [portal/tests/e2e/\_helpers.py](portal/tests/e2e/_helpers.py) (backing the one-off `docker run`/`docker build` calls in `_edge_helpers.py`, `test_tunnel.py`, and `test_mta_real.py`), and the two explicit `tags:` in [.github/workflows/test.yaml](.github/workflows/test.yaml) (the `docker/bake-action` steps inherit their tags from `image:` and need no separate edit). E2e portal services also set `SHADOWSOCKS_IMAGE=local/shadowsocks-server-test` so newly-created `ss-*` containers spawn from the e2e image instead of `Settings.shadowsocks_image`'s production default — this only controls which image *new* containers are created from; it does **not** scope container ownership across stacks (the reconciler's orphan sweep and `cleanup_all_containers()` key solely on the `postern.managed` label, not on image — see issue #197). Production still builds `local/shadowsocks-server` (and the other five images) unsuffixed by hand; the invariant is that *e2e* never writes an unsuffixed tag, not that nobody does. Pinned by [portal/tests/test_e2e_image_isolation.py](portal/tests/test_e2e_image_isolation.py), which derives the banned set from `compose*.yaml` + `Settings` and globs every path it scans, so a new file or a new production service is covered automatically.
- **Portal build context is also the repo root, not `./portal/`.** [portal/Dockerfile](portal/Dockerfile) `COPY`s `LICENSE.md` from the repo root for AGPL §5(a) compliance and uses `portal/`-prefixed paths for its own sources. [compose.yaml](compose.yaml) and [portal/tests/e2e/e2e.compose.yaml](portal/tests/e2e/e2e.compose.yaml) both set `context:` accordingly. A `docker build ./portal/` command will fail.
- **mta and provisioner build context is also the repo root.** Both [mta/Dockerfile](mta/Dockerfile) and [provisioner/Dockerfile](provisioner/Dockerfile) `COPY portal/src/postern/mta /usr/lib/python3.13/site-packages/postern_mta` so the DKIM rendering / verification logic is shared between portal CLI, mta entrypoint, and provisioner entrypoint. Compose's `build:` does **not** detect cross-service file deps — when [portal/src/postern/mta/dns.py](portal/src/postern/mta/dns.py) changes, both `docker compose build mta provisioner` must re-run.
- **The mta and provisioner are split deliberately.** The mta holds the DKIM signing key and is exposed on public port 25. The provisioner holds the DNS provider API token and has zero inbound listeners. A Postfix RCE on port 25 cannot escalate to DNS-record hijack because the credentials live in a different container. Do **not** "consolidate for simplicity."
- **mta is intentionally non-distroless and non-read-only.** The runtime is `dhi.io/alpine-base:3.23` (busybox + Python 3). Postfix and OpenDKIM write to many paths during normal operation (`postmap`-compiled `*.db`, `/etc/resolv.conf`, queue management). The portal's `read_only: true` pattern is dropped here; security comes from `cap_drop: [ALL]` plus a minimal `cap_add` set ([compose.yaml](compose.yaml) `mta:`).
- **opendkim runs as UID/GID 110:110 in both mta and provisioner**, pinned in both Dockerfiles ([mta/Dockerfile](mta/Dockerfile) and [provisioner/Dockerfile](provisioner/Dockerfile) call `addgroup -g 110 -S opendkim && adduser -u 110 -S -G opendkim`). The provisioner runs as this user (compose `user: "110:110"`) so files it writes to the shared `postern-mta-data` volume are readable by mta's opendkim. Do not let Alpine package version drift change this.
- **`mynetworks` is scoped to the `mta-submit` /29 subnet only** ([mta/etc/main.cf.tmpl](mta/etc/main.cf.tmpl); IPAM-fixed `172.30.42.0/29` in [compose.yaml](compose.yaml) `mta-submit:`), not the shared `default` bridge. Only the `portal` joins `mta-submit`. Adding any other service to `mta-submit` would let it relay through mta without authentication. If a future feature genuinely needs to submit, add SASL or use a separate network.
- **Built-in-MTA submission goes through the `mta-submit` network *alias*, never the bare `mta` name.** The `mta` service is multi-homed (`default` + `mta-submit`); Docker's embedded DNS resolves the bare `mta`/`postern-mta` name to one of its network IPs — in practice the **default**-network IP, not deterministically the internal one (issue #151) — so a portal connecting to `mta` submits from the default network, outside `mynetworks`, and Postfix rejects (`554 5.7.1 ... Access denied`). The `mta` service therefore carries `aliases: [mta-submit]` on the `mta-submit` network ([compose.yaml](compose.yaml) `mta:`) and `example.env` sets `SMTP_HOST=mta-submit`; the connection then lands on the internal /29 (source ∈ `mynetworks`). Neither `compose.cert.yaml` nor `compose.gateway.yaml` overrides `mta.networks`, so the alias survives every documented `COMPOSE_FILE` combination — an overlay that *does* touch `mta.networks` must re-add it. [email.py](portal/src/postern/email.py)'s skip-cert-validation list covers both `mta` and `mta-submit`. The alias plus the `mta-submit` subnet ↔ `MTA_SUBMIT_CIDR` ↔ `mynetworks` agreement are pinned by [portal/tests/test_compose_submission.py](portal/tests/test_compose_submission.py); the maintainer `e2e-mta-real` overlay mirrors it.
- **`milter_default_action = tempfail`** ([mta/etc/main.cf.tmpl](mta/etc/main.cf.tmpl)). If opendkim is down, mail queues rather than going out unsigned. An unsigned outbound from this MTA defeats DMARC `p=reject` and is worse than delayed delivery. Don't change to `accept` "for resilience."
- **DANE outbound requires the local Unbound resolver** in the mta container. `smtp_tls_security_level = dane` is a silent no-op without DNSSEC validation. The mta entrypoint writes `/etc/resolv.conf` to point at `127.0.0.1:53` (Unbound). Removing Unbound silently degrades outbound TLS to `may`.
- **Postfix queue lives in the `postern-mta-queue` named volume.** Putting it on tmpfs would lose deferred mail on every container restart — including greylist-deferred OTPs that are about to retry. tmpfs for the queue is wrong even at low volume.
- **DKIM key sharing.** `postern-mta-data` is mounted rw on mta, provisioner, and portal. The portal's `postern mta show-dns` reads `<selector>.txt` and state.json; `postern mta rotate-dkim` writes the `.rotate-dkim` trigger file there. The provisioner is the only writer of `state.json` (see `rotation.write_state` docstring) — the rw portal mount is for trigger files only. No HTTP listener.
- **Trigger files mirror the reconciler pattern.** [portal/src/postern/mta/rotation.py](portal/src/postern/mta/rotation.py) defines two: `.rotate-dkim` (portal CLI -> provisioner) and `.reload-opendkim` (provisioner -> mta). Existence is the signal; consumer deletes after handling. Same race acceptance as `.reconcile-now` at [reconciler.py:163](portal/src/postern/reconciler.py#L163): double-trigger may collapse, which is fine because the state machine is idempotent.
- **MTA-STS policy is served by nginx**, not by mta. The `mta-sts.<domain>` server block at [nginx/etc/conf.d/mta-sts.conf](nginx/etc/conf.d/mta-sts.conf) is load-bearing for the MTA-STS standard (RFC 8461 §3.3 mandates HTTPS with a publicly-trusted CA). Outbound MTA-STS enforcement (consuming recipient policies) is via `postfix-mta-sts-resolver` running inside mta.
- **e2e-mta uses a static IP for `MTA_E2E_TRANSPORT_OVERRIDE`.** The mta entrypoint rewrites `/etc/resolv.conf` to point at local Unbound (127.0.0.1), and CI runners cannot reach root nameservers. Two consequences: (1) the e2e-mta overlay [portal/tests/e2e/e2e-mta.compose.yaml](portal/tests/e2e/e2e-mta.compose.yaml) targets a fixed IP (`smtp:[172.30.99.10]:1025`, mailpit pinned via IPAM) instead of a hostname, so Postfix never does DNS lookup for the next hop; (2) it bind-mounts a test-only [portal/tests/e2e/unbound.e2e-mta.conf.tmpl](portal/tests/e2e/unbound.e2e-mta.conf.tmpl) over `/usr/local/share/mta-templates/unbound.conf.tmpl` that declares `postern.test` and `elsewhere.test` authoritatively (so `reject_unknown_sender_domain` passes for `noreply@postern.test`). Switching to a hostname requires either dropping that Unbound override or providing a real DNS environment.
- **`postern-dns` (the libdns wrapper) lives in the provisioner only.** The DNS provider API token is in the provisioner's env (`DNS_PROVIDER` plus libdns-native env vars like `CLOUDFLARE_API_TOKEN`). The mta image does not have it and cannot publish/retire DNS records. The same provisioner also ships `lego` for ACME DNS-01 cert renewal (see [provisioner/Dockerfile](provisioner/Dockerfile)); both binaries share the same provider env vars.
- **Two TLS cert deployment modes.** BYO certs (default, host `/etc/letsencrypt` bind-mount, base [compose.yaml](compose.yaml)) or auto-renewal ([compose.cert.yaml](compose.cert.yaml) override + `with-cert-renewal` profile + `CERT_RENEWAL=true`). Don't conflate them — running both leads to two writers fighting over the same paths. The `postern-letsencrypt` named volume is populated by the provisioner under auto-renewal; it is empty in BYO mode.
- **Wildcard cert SAN list is exactly `{<domain>, *.<domain>}`.** Adding subdomain SANs (`mail.<domain>`, `mta-sts.<domain>`, etc.) leaks them to Certificate Transparency logs and defeats the whole reason we use a wildcard. The `postern cert verify` command pins this; `postern_provisioner.cert.expected_sans_for` returns this set; `[postern.cert.inspect.CertInfo.sans_match](portal/src/postern/cert/inspect.py)` enforces exact-set equality.
- **Cert state machine** is `NO_CERT → ISSUING → ISSUED_PENDING_INSTALL → INSTALLED → RENEWING → ISSUED_PENDING_INSTALL → INSTALLED`. `FAILED` is non-terminal (60-min hold-off then retry the prior pre-FAILED state). `last_issued_iso` is recorded BEFORE calling Lego to defend LE rate limits even on partial-failure paths. 24-hour rate-limit guard on top, with `CERT_FORCE_REISSUE=true` operator override. Persisted at `/etc/letsencrypt/state.json`.
- **Atomic cert install uses symlink-flip, not directory rename.** `os.replace` on a non-empty directory returns `ENOTEMPTY`. [postern_provisioner.install](portal/src/postern_provisioner/install.py) writes to `live/<domain>.<timestamp>/` then `os.replace`s a sibling temp symlink into `live/<domain>`. Concurrent readers see either old or new — never torn.
- **Cert renewal trigger files** mirror the DKIM rotation pattern: `.renew-cert` (portal CLI → provisioner, on the cert volume) and `.reload-mta-tls` (provisioner → mta, on `postern-mta-data`). Existence is the signal; consumer deletes after handling. Idempotent state machines tolerate double-trigger collapse.
- **First-issuance bootstrap via `depends_on: condition: service_healthy`.** Under [compose.cert.yaml](compose.cert.yaml), nginx and mta wait on the provisioner's healthcheck ([healthcheck.py](portal/src/postern_provisioner/healthcheck.py)), which only flips healthy when (a) DKIM has a key, AND (b) if `CERT_RENEWAL=true`, cert state shows `INSTALLED`. `service_healthy` gates startup only; once dependents are running, provisioner becoming unhealthy doesn't stop them. Provisioner uses `restart: unless-stopped` (not `restart: "no"`) when cert renewal is on, so transient outages self-heal.
- **`DNS_PROVIDER` is shared by DKIM rotation and cert renewal.** Same env var; same provider account. Each subsystem has its own enable flag (`with-mta` profile membership for DKIM, `CERT_RENEWAL=true` for cert renewal).
- **Wildcard `privkey.pem` is mode 0644 (world-readable in-container).** The DHI nginx distroless image has no root user in `/etc/passwd`, so we cannot add the existing nginx user to gid 110 at image build time. The single-tenant trust boundary is "anyone with shell access in any container is already admin-equivalent", so 0644 is an acceptable degradation. See [postern_provisioner.install](portal/src/postern_provisioner/install.py).
- **CSP forbids inline.** Nginx sets `Content-Security-Policy: default-src 'self'` on every portal response ([nginx/etc/nginx.conf.tmpl:34](nginx/etc/nginx.conf.tmpl#L34)). That blocks inline `<style>` blocks, inline `<script>` blocks, and HTML event-handler attributes (`onclick=`, `onerror=`, etc.). All CSS lives in [portal/src/postern/static/postern.css](portal/src/postern/static/postern.css); all JS in [portal/src/postern/static/postern.js](portal/src/postern/static/postern.js); event handlers attach via `addEventListener`. Templates contain zero `<style>`/`<script>` blocks and zero `on*=` attributes. Test coverage: `test_login_uses_external_css_and_js`, `test_login_has_no_inline_event_handlers` in [portal/tests/test_routes.py](portal/tests/test_routes.py).
- **Identity card IP source.** [identity.\_client_ip](portal/src/postern/identity.py) trusts `X-Real-IP` only when the direct socket peer is in an actual RFC1918 / ULA / loopback / link-local range -- NOT `ipaddress.is_private`, which is too broad (it includes TEST-NET-3 `203.0.113.0/24`, used legitimately as a public source IP in tests and docs). Bypassing this with `request.client.host` directly works under nginx today but fails closed in any future deployment that ever puts portal behind a different reverse proxy or exposes it directly.
- **`/brand-icon` indirection.** Templates reference `/brand-icon`, never `/static/brand-default.svg` directly. The route ([portal/src/postern/routes/brand_icon.py](portal/src/postern/routes/brand_icon.py)) validates extension (.svg/.png), resolves the path canonically, caps size at 256 KB, and falls back to the built-in default on any error so a misconfigured `PRODUCT_ICON_PATH` never takes the portal down.
- **MMDB reader lifecycle.** `GeoIPReaders` ([portal/src/postern/identity.py](portal/src/postern/identity.py)) is constructed at lifespan startup, lazily opens MMDB files on first lookup, re-opens them when the underlying file's mtime advances (so monthly DB rotations need no portal restart), and is closed at lifespan shutdown. `maxminddb.Reader.get()` is thread-safe; the lazy-init / reopen path holds an internal `threading.Lock`. `GeoIPReaders("")` is a valid no-op constructor.
- **No inline JS bootstrap.** [portal/src/postern/static/postern.js](portal/src/postern/static/postern.js) is wrapped in an IIFE and self-bootstraps on `DOMContentLoaded`. Templates never call into it. Adding template-side JS is forbidden (CSP); add new behavior to `postern.js` and gate it on element presence (`if (!el) return;`).
- **Build provenance is a three-place chain.** `GIT_REVISION` build arg (all five first-party Dockerfiles) → `org.opencontainers.image.revision` label (+ `POSTERN_REVISION` env on the portal, read by `postern version`) → [scripts/verify-deploy.py](scripts/verify-deploy.py), which fails a deploy whose containers are not on images built from `HEAD`. A new first-party image must add the `ARG`/`LABEL` pair as the last instruction of its final stage and, if compose builds it, forward `GIT_REVISION: ${GIT_REVISION:-}` in `build.args`. Pinned by [portal/tests/test_build_revision.py](portal/tests/test_build_revision.py). The gate also asserts a container's health status (from its Docker `HEALTHCHECK`, when one is defined) is not `unhealthy` — point-in-time, not polled: `starting` (the status right after `up -d`, before the first probe) passes. It is host-side on purpose: desired state lives in the compose files, which the portal cannot read, and a stale portal cannot be trusted to report its own staleness. `--tunnels` (opt-in; the reconciler recreates `ss-*` containers asynchronously after a portal restart, so it races a bare `up -d`) scopes to this deployment's own `postern.instance` label, mirroring `reconciler.resolve_instance_id`, so a host running more than one Postern deployment does not report a different deployment's tunnels as this one's.
- **Deploying goes through `scripts/deploy.sh`.** The shadowsocks image is built outside compose and everything else inside it, so running only one command leaves a half-new, healthy, wrong stack. The script refuses a dirty / behind-`origin/main` / non-`origin/main` checkout (`--allow-dirty`/`--allow-behind`/`--allow-branch`/`--no-fetch` are the explicit overrides; `origin`/`main` are hardcoded, not flags), resolves and stamps `GIT_REVISION`, builds `local/shadowsocks-server` (or whatever `SHADOWSOCKS_IMAGE` the portal image itself resolves — asked via a throwaway `docker compose run`, never read from the deploying shell's environment, since compose only ever hands the portal that variable through `env_file: .env`) from the repo root, runs `docker compose up -d --build`, blocks on `postern reconcile --wait --wait-timeout 1800` (30 minutes; `deploy.sh`'s own `--wait-timeout` overrides it — the CLI's own default of unbounded is deliberately NOT used here, since `reconciliation_loop` is a single unsupervised background task and an unbounded wait would hang the script forever if it ever died independently of a slow pass), and finally runs `scripts/verify-deploy.py --tunnels`, forwarding `--allow-dirty` when the deploy itself allowed one. It passes no `-f`/`--profile` flags — `COMPOSE_FILE`/`COMPOSE_PROFILES` come from `.env`, so every documented overlay combination (cert/gateway/edge) works unchanged. `--tunnels` is safe here specifically because the blocking reconcile guarantees a completed pass first. Tested by [portal/tests/test_deploy_script.py](portal/tests/test_deploy_script.py), which puts fake `git`/`docker`/`python3` executables on `PATH` and asserts the exact command sequence — no live Docker daemon, network, or deploy host involved. Adding a deploy step means adding it here, not to a docs page. CI lints this script through `test.yaml`'s `lint` job; run `prek run --all-files` locally before pushing a change to it.
- **prek is the CI lint gate, and its own orchestration is tracked shell, not inline YAML.** [.github/workflows/test.yaml](.github/workflows/test.yaml)'s `lint` job runs `uv run --project portal --group dev prek run --all-files` against the repo's own [prek.toml](prek.toml) — the same config the local pre-commit hook uses, so CI and the hook cannot drift. `prek` is a `portal/` dev dependency pinned by `portal/uv.lock` exactly like `ty` and `yapf`, so Renovate's uv support bumps it; `--project` rather than `--directory` is load-bearing, since prek must run with CWD at the repo root to find `prek.toml` and the git root. This job is also the *only* place CI type-checks — `mta/entrypoint.py` and `provisioner/entrypoint.py` are the current exceptions, tracked as issue #220; see prek.toml's own comment on the `ty` hook for why the roots stop at `scripts/`/`docs/` and don't yet include them. The job's `run:` steps are one-liners calling [scripts/ci-lint-selftest.sh](scripts/ci-lint-selftest.sh) and [scripts/ci-lint-run.sh](scripts/ci-lint-run.sh) — tracked files, so prek's own shellcheck hook lints them on every run, closing the gap a fully-inline job would leave (shellcheck cannot parse embedded YAML `run:` blocks at all); both import their file-matching and dry-run-parsing logic from [scripts/ci_lint_lib.py](scripts/ci_lint_lib.py). `ci-lint-selftest.sh` briefly writes real, type-broken fixture files into `portal/src/postern/`, `scripts/`, and `docs/`, so it refuses to run outside CI (`$CI=true`, set automatically by GitHub Actions) unless passed `--force-local` — a concurrent `prek run`/`git commit` in the same checkout would otherwise see a fixture as a genuine type error. A green run proves less than it looks. Five guards close the gaps — see each script's/module's own header comment or docstring for the mechanism and why it must cover the full hook set, not a subset. shellcheck only scans tracked files `identify` tags `shell`; it does **not** parse Dockerfile `RUN` bodies (issue #212).

## Style deltas

Global convention: Python is yapf-formatted, type-hinted, and section-comment-annotated. The formatter for section comments is [scripts/format-section-comments.py](scripts/format-section-comments.py):

- Primary section: `# <name> =====`
- Sub-section: `# <name> -----`

That script is ALSO a pytest module (the tests live in the same file). If you find yourself "cleaning up dead code" there, stop — you are looking at its test suite.

Type checking is `ty` (invoked via `uvx ty check` in prek).

Commit subjects follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/): `type(scope): subject`. Allowed types: `feat`, `fix`, `refactor`, `chore`, `ci`, `docs`, `test`, `build`, `perf`. Scope is optional but encouraged (e.g. `cli`, `portal`, `shadowsocks`, `nginx`, `deps`). The subject stays single-line; trailers like `Approved-By:` go after a blank line and are reserved for tool-generated metadata. Renovate is configured to follow the same convention via `semanticCommits` in [.github/renovate.json](.github/renovate.json).

## Do-not list

- Don't change the nginx path regex without updating `token_hex(12)` in `cli.py` and `_container_name` in `reconciler.py`.
- Don't mutate a shipped migration to allow a new plugin value (or change any other historical schema). Migrations are immutable once published; add a new migration N+1 instead. To add a third plugin, add migration 4 that ALTERs the CHECK constraint via the table-rebuild pattern.
- Don't create Shadowsocks containers outside the reconciler.
- Don't filter a container listing on `postern.managed=true` alone when the result feeds a create/remove/start decision. Always conjoin `postern.instance=<id>` (`reconciler._list_managed_containers`'s pattern) — a bare `postern.managed=true` filter matches every Postern deployment sharing this Docker daemon, not just this one. The one deliberate exception is `_report_legacy_running_containers`'s read-only listing, which needs the bare label to distinguish "no instance label" (legacy) from "a different instance's label" (foreign) — it never removes anything and skips any container carrying an instance label.
- Don't auto-remove or auto-adopt a container on a create-time name conflict or in the disabled-connection check unless it's already labelled for this exact instance (`postern.managed=true` AND `postern.instance=<this instance's id>`). Ownership of an unlabelled or foreign-instance container can't be proven safely; log manual `docker rm -f` guidance instead (see `reconciler._log_name_conflict`).
- Don't resolve the reconciler's own instance identity via live Docker self-inspection (e.g. reading the running container's own labels back from the API). Use `reconciler.resolve_instance_id(settings)`, which is pure configuration (`INSTANCE_ID` override, else `Settings.compose_project_name`) — adding a Docker round-trip to the identity check adds a startup-time failure mode the check exists to avoid.
- Don't bypass `db.get_connection()` with a raw `aiosqlite.connect()`.
- Don't open an aiosqlite connection without `async with db.get_connection(...) as conn:` (or fixture teardown). The aiosqlite worker is a non-daemon `Thread` and a missed `close()` hangs interpreter exit forever after pytest finishes. `db.get_connection` is an `@asynccontextmanager` exactly to make this impossible to get wrong.
- Don't simplify `hmac.compare_digest` to `==`.
- Don't remove the `__dummy__{email}` path in `auth.request_otp`.
- Don't rename the `session` or `otp_email` cookies.
- Don't re-enable `docs_url` / `redoc_url` / `openapi_url`.
- Don't commit to anything under `external/` — use `git subrepo pull` / `push`.
- Don't hardcode `/var/run/docker.sock`; access goes through `docker-proxy`.
- Don't write tests or code that assume `./data/postern.db` or that `ss-*` containers persist across portal restarts.
- Don't change `OTP_EXPIRY_SECONDS` without also updating the `otp_email` cookie `max_age` in [routes/login.py](portal/src/postern/routes/login.py).
- Don't build the shadowsocks image with `docker build ./shadowsocks/` — the Dockerfile pulls from `external/` and needs the repo root as context.
- Don't let anything on the e2e side name an unsuffixed `local/<name>` image. E2e builds `local/<name>-test`; tags are host-wide and an e2e run must never overwrite what production deploys. Add new e2e image refs as constants in [portal/tests/e2e/\_helpers.py](portal/tests/e2e/_helpers.py).
- Don't add shell-form `RUN`, `CMD`, or `HEALTHCHECK` in the runtime stage of [portal/Dockerfile](portal/Dockerfile), and don't use `[CMD-SHELL ...]` for the portal in compose. The runtime is distroless. Use Python (`python -c '...'`) or move shell work to the build stage.
- Don't drop `init: true` (compose) or `init=True` (`containers.run` kwarg) when adding a new service or container launch. Every container in this repo runs with tini at PID 1 — see the **PID 1 is `tini`** invariant.
- Don't write commit subjects that don't follow Conventional Commits 1.0.0 — applies to humans, AI agents, and Renovate equally.
- Don't put the DNS provider API token in any container other than the provisioner. The mta is exposed on public port 25; cross-container credential sharing defeats the split-container attack-surface argument.
- Don't set `MTA_REQUIRE_DNSSEC=false` in production. The default `auto` infers and enforces for signed domains; `false` disables the startup safety check entirely. Use `=true` only when you want fail-closed for unsigned-domain detection. Without DNSSEC, MTA-STS and DKIM records can be silently tampered with by anyone with upstream-DNS access — defeating most of what the rest of the security configuration buys you.
- Don't put `/var/spool/postfix` (the Postfix queue) on tmpfs. Mail in flight is lost on container restart.
- Don't set `milter_default_action = accept` in [mta/etc/main.cf.tmpl](mta/etc/main.cf.tmpl). If opendkim is down, mail must queue, not escape unsigned.
- Don't point `SMTP_HOST` at the bare `mta` (or `postern-mta`) name for the built-in MTA, and don't drop the `mta-submit` alias from the `mta` service's `mta-submit` network. The multi-homed `mta` name resolves to the default-network IP and fails Postfix `mynetworks` (issue #151). Use `SMTP_HOST=mta-submit`.
- Don't change opendkim's UID/GID away from 110 in either [mta/Dockerfile](mta/Dockerfile) or [provisioner/Dockerfile](provisioner/Dockerfile) without changing both. The shared volume permissions depend on them matching.
- Don't add subdomain SANs (mail., mta-sts., etc.) to the wildcard cert. The exact-set match `{<domain>, *.<domain>}` is load-bearing for CT-leak hygiene.
- Don't run a host-side certbot when [compose.cert.yaml](compose.cert.yaml) is active. Two writers on `/etc/letsencrypt` will fight.
- Don't `os.replace` a non-empty directory expecting atomic semantics. Use the symlink-flip pattern in [postern_provisioner.install](portal/src/postern_provisioner/install.py).
- Don't run two provisioner replicas under auto-renewal. Lego's account storage isn't concurrency-safe.
- Don't make the zone-ECH reconciler call `ech-set off` or flip the setting back on disable — it is zone-wide; converge-to-ON only.
- Don't gate the provisioner healthcheck's ECH half on live DoH propagation; gate on the PATCH-success state (`ech_zone_state.json`), or a slow CF publish deadlocks startup.
- Don't call the Cloudflare settings API from the portal — the portal has no `CLOUDFLARE_API_TOKEN`; `postern ech verify`/`show` are DoH-only.
- Don't make the zone SSL/TLS-mode reconciler downgrade, revert, or bump `full`→`strict`; it is raise-only (floor `full`) and converge-only. Don't call `ssl-set` with `off`/`flexible` (only `full`/`strict` are valid targets).
- Don't flip `EDGE_CF_MANAGE_SSL_MODE` to opt-in to match zone-ECH; SSL-mode management is deliberately default-on (opt-out) because a Flexible/Off zone is a hard `ERR_TOO_MANY_REDIRECTS` breakage.
- Don't call the Cloudflare settings API from the portal; `postern edge ssl-status` reads `ssl_mode_state.json` only.
- Don't build a first-party image without `--build-arg GIT_REVISION` (or `export GIT_REVISION` for compose builds). An unstamped image has no provenance and `scripts/verify-deploy.py` fails it.
- Don't treat `docker compose ps` showing `Up` or `/healthz` returning 200 as deploy evidence. They are liveness, not version.

## Useful commands

```bash
# The whole deploy sequence, in one command. Refuses to run against a dirty or
# out-of-date checkout, and exits non-zero unless the running stack is provably on
# the images just built (includes mta + provisioner via COMPOSE_PROFILES=with-mta
# in .env).
scripts/deploy.sh

# The same sequence, spelled out, for debugging:
GIT_REVISION="$(scripts/verify-deploy.py --print-revision)"
export GIT_REVISION
docker build -f shadowsocks/Dockerfile --build-arg GIT_REVISION="$GIT_REVISION" -t local/shadowsocks-server .
docker compose up -d --build
docker compose exec -T portal postern reconcile --wait
scripts/verify-deploy.py --tunnels

# Run the admin CLI
docker compose exec portal postern user list
docker compose exec portal postern user add "Name" email@example.com
docker compose exec portal postern connection add email@example.com "label"

# Built-in MTA admin
docker compose exec portal postern mta show-dns          # canonical DNS records to publish
docker compose exec portal postern mta verify-dns        # check DNS state matches
docker compose exec portal postern mta dnssec-status     # check AD bit on the sending domain
docker compose exec portal postern mta rotate-dkim       # request a rotation step
docker compose exec portal postern mta rotation-status   # show rotation state machine

# Manual reconcile trigger (bypasses the 60s poll)
docker compose exec portal postern reconcile

# Tail logs
docker compose logs -f portal
docker compose logs -f nginx
docker compose logs -f mta
docker compose logs -f provisioner

# Shell into the shadowsocks image (ENTRYPOINT execs ssserver -- override to get a shell)
docker run --rm -it --init --entrypoint sh local/shadowsocks-server

# Tests
cd portal && uv run pytest

# Full prek run
prek run --all-files
```
